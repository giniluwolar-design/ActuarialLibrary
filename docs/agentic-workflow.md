# An agent-assisted actuarial workbench

The Python package is already independent of the UI. Streamlit is its current human interface; it is not the calculation engine. An agent can call the same functions. A chat box alone would not make the workflow agentic.

## Proposed workflow

1. The user gives an objective: “Review the Liability reserve, investigate unusual development and compare with our prior approved valuation.”
2. The agent checks the data contract, valuation cutoffs and completeness, then builds paid, incurred and count triangles.
3. It inspects link ratios, credibility of mature ages, calendar-period patterns and method disagreement. `review.observation_pairs` exposes exact fitting membership and weights.
4. It proposes exclusions or alternative assumptions with reasons and calculates labelled scenarios. Original observations remain available. A proposed scenario is not an approved actuarial selection.
5. It compares like-for-like scenarios using `review.method_impact`. A reserve movement across valuations additionally requires the earlier data and assumptions. The agent must not call an assumption sensitivity a calendar-period movement, or infer a business cause solely from a numerical change.
6. The actuary reviews scenarios and confirms the final selection. The agent prepares a narrative and reports from the recorded analysis result.

## Numerical and reporting boundaries

Every numerical assertion should reference a run, origin, method, metric and assumption set. Reports should be generated from structured results, with the language model responsible for drafting narrative rather than recomputing numbers. A Word report, PowerPoint committee deck and Excel supporting schedules can share the same run identifier and reconciliation tables. The existing worked Excel is an educational example, not the model for an arbitrary uploaded portfolio; a per-analysis workbook exporter is a separate implementation.

A report should distinguish findings, hypotheses and data limitations. Examples: a measured increase in incurred development is a finding; a change in claims handling is a hypothesis until corroborated. Drafts should disclose exclusions, tails, missing priors and unavailable methods.

## Bootstrap is a separate validated calculation tool

Bootstrap cannot be added responsibly as an instruction to a language model. Define a residual bootstrap model and its assumptions, residual adjustment, treatment of negative incremental observations, tail uncertainty, process versus parameter risk, simulation seed and convergence checks. Validate against independent implementations and hand-checkable cases before exposing percentile reserves. The present library remains deterministic; no bootstrap results are generated by the UI.

## Connection choices

A local-first MCP tool server could expose validation, triangle building, observation review, reserving, scenario comparison and export as narrow typed tools. A chat client would orchestrate those calls. It needs explicit workspace/run identifiers, bounded simulation workloads, immutable run snapshots and controlled file output paths. Those controls are distinct from the current reproducibility metadata, which is not a tamper-proof log.

Alternatively, the app can connect directly to a model provider. That requires choosing the provider and deciding what may leave the computer. Aggregated triangle data may still be confidential. Do not silently send claims or analysis results to a hosted model. A local model is another possible deployment, with capability and hardware trade-offs.

## Try the local agent now

Use the **Your AI analyst** panel alongside the three-step workspace and choose **Connect to local Gemma**. Ollama must be running on this computer at `127.0.0.1:11434`. Choose an installed model (the development machine has `gemma4:latest`), then click a starter question or type your own. No model download, API key or external account is required when Gemma is already installed.

Examples:

- “Review the latest origin and explain the difference between paid and incurred Chain Ladder.”
- “Inspect the paid age 1 to 2 observations. Which deserve investigation?”
- “Exclude 2020 from paid age 1 to 2 as a sensitivity and show the ultimate impact.”
- “Test a paid tail of 1.05 against the current assumptions.”

The agent uses native Ollama tool calls. Eight allowlisted tools retrieve an overview, explain the API and methods from controlled notes, inspect factors, inspect observation pairs, retrieve origin results, compare scenarios, inspect current claim-size diagnostics and create artifacts. Python validates arguments and calculates all tool results. No model-generated Python or shell commands are executed. Tool calls are bounded to six model rounds with at most four tool calls per round; each local request has a timeout. The model may still make errors in its narrative: inspect the evidence IDs beside its claims.

Ask “Make a report” for an actual Markdown draft containing calculated method estimates, reserve components, full assumptions, metadata and diagnostics. Specify a known scenario ID to report that scenario; otherwise the report uses the UI assumptions. Ask “Make test data” for a reproducible synthetic CSV ZIP with coverage and instructions. No latent future outcomes are included. These files appear in the panel as downloads; the model cannot write arbitrary file paths. Word/PowerPoint and per-analysis formula Excel are still outside this implementation.

Scenarios start from the current UI assumptions each time. Follow-up scenarios do not implicitly compound earlier chat scenarios. They do not change the UI selections. Download each scenario's CSV/JSON package and the chat/evidence JSON before changing the data, assumptions or model, or starting a fresh chat. Chats reside in application session memory, not a persistent conversation database. A reload may reset the session.

The connector uses a fixed loopback endpoint, bypasses environment proxies, rejects HTTP redirects and rejects remote-backed/cloud model names. Prompts and tool evidence are passed to your local Ollama service. Tool evidence includes aggregated results and analysis metadata; individual claim records are not exposed. Model responses are exploratory drafts, not approval decisions.

Implemented: connected local chat, bounded tool orchestration, factor/observation investigation, separate scenarios and downloadable evidence/results. Not implemented: an MCP server, prior-valuation movement decomposition, bootstrap, or Word/PowerPoint/per-analysis formula-Excel generation. The worked Excel remains an educational example.

For developers, `python scripts/check_local_agent.py` runs an optional real-model test with synthetic Motor data and writes an ignored local evidence record. Unit tests use a fake transport and do not require Ollama. See the official [Ollama chat API](https://docs.ollama.com/api/chat) for the native tool-call interface used here.
